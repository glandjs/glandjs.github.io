Frameworks are trade-offs. This page states Gland's, so you can decide whether they are
the ones you want to make — and it tries to be as useful to you when the answer is no.

## The trade, in one sentence

You give up Nest's ecosystem, its conventions and its batteries, and in return you get
two things: **side effects that are addressable by name**, and **a transport that is a
replaceable part rather than the shape of your application.**

That is a narrow trade. It is worth it if your domain logic is real. It is not worth it
if your controller body is one database read.

## What you actually write

Take the flow everyone already knows:

```text
OrderCreated
 ├── Payment
 ├── Notification
 ├── Inventory
 ├── Analytics
 └── Coupon
```

### The service-class version

```ts
// order.service.ts
@Injectable()
export class OrderService {
  constructor(
    private readonly payment: PaymentService,
    private readonly inventory: InventoryService,
    private readonly notification: NotificationService,
  ) {}

  async create(dto: CreateOrderDto) {
    const order = await this.repo.save(dto)
    await this.payment.charge(order)
    await this.inventory.reserve(order)
    await this.notification.confirm(order)
    return order
  }
}
```

Adding `Analytics` means opening `OrderService`, injecting one more thing, and adding a
line to a method that is now four side effects long. There is no seam — the
dependencies are constructor arguments, so the shape of the work is the shape of the
class.

### The Gland version

```ts
// shared/events.ts — one map, the whole contract
export type AppEvents = {
  'order:created': IOEvent<{ orderId: string; total: number }, Order>
}

// order.channel.ts
@Channel('order')
export class OrderChannel {
  @On('created')
  async create(payload: EventPayload<AppEvents, 'order:created'>): Promise<Order> {
    return this.repo.save(payload)
  }
}

// payment.channel.ts
@Channel('payment')
export class PaymentChannel {
  @On('order:created')          // namespaced to payment:order:created
  async charge({ orderId }) { /* … */ }
}

// inventory.channel.ts
@Channel('inventory')
export class InventoryChannel {
  @On('order:created')
  async reserve({ orderId }) { /* … */ }
}
```

```ts
// order.controller.ts — translates and replies
@Controller('/orders')
export class OrderController {
  @Post()
  async create(ctx: HttpContext<AppEvents>) {
    return ctx.call('order:created', { total: 42 })
  }
}
```

`OrderChannel` imports no other channel. `PaymentChannel` imports nothing from the
order side. Adding `Analytics` is a new file registered in the module — `OrderChannel`
and `OrderController` are untouched.

<Aside type="note" title="This is not pub/sub, and that is the point">
  `emit()` is broadcast: fire-and-forget, every listener, no return value.
  `ctx.call()` is the other thing — **addressed request/response** to one named
  channel, with the result type declared by `IOEvent<Payload, Return>`. It is a
  service lookup that resolves by name at runtime instead of by import at compile
  time, and it is what makes the controller above return an `Order`.
</Aside>

The trade is real in both directions: indirection you can feel while reading, and the
extra file. You are buying the ability to change a side effect without editing a class
that already knows about five of them.

## Compared to a service class

This is the honest alternative — what most codebases would build if not for Gland.

| | Service classes | Gland |
| --- | --- | --- |
| Controller depends on | injected instances | the event map |
| Side effects live in | services, wired by hand | channels, registered by name |
| Adding a side effect | edit the controller and its constructor | add a channel to the module |
| Order of side effects | the order you wrote in the method | the order handlers register |
| Testing one side effect | construct it with fakes | call it with a fake context |
| Removing a side effect | find every import of it | delete the file |

The row that decides it for most people is **adding a side effect**. Everything else is
a matter of taste.

## Compared to Nest

Nest is a mature framework solving a different problem well, and its
`@nestjs/event-emitter` is genuinely the same primitive: an in-process emitter. So if
your reason for choosing Gland is "it has events and Nest does not", that reason is
wrong.

Where they actually differ:

| | Nest | Gland |
| --- | --- | --- |
| Units are | classes, wired by constructor | channels, addressed by name |
| A side effect is reached by | an import | `ctx.call('name', payload)` |
| Replace the HTTP layer | replace Nest's abstractions | swap `@glandjs/express` for `@glandjs/node` |
| Ecosystem | large, the reason most people choose it | small; you assemble the rest |
| Convention | strong, and enforced | loose; there is less to learn and less to fight |

Read the first three rows as one sentence: **Gland's unit of composition is a named
capability, not a class.** That is a real difference and it is the only one. If your
team values Nest's ecosystem and conventions more than that, Nest is the right answer
and nothing here should convince you otherwise.

## Where the cliff is

This is the section that matters most when you are evaluating Gland, and it is the one
people find out about in production.

**Gland's events do not leave the process.** `EventBroker.connectTo(broker)` takes a
broker *instance*. There is no serialisation, no acknowledgement and no network hop.

That buys speed and simplicity, and it has four consequences you must design around:

| | Consequence |
| --- | --- |
| **Scale out** | With three app servers behind a load balancer, an event emitted on one does not reach listeners on the other two. Whatever listens must be reachable on the process that emitted. |
| **Durability** | A crash between `emit()` and the listener running loses the event. There is no replay and no dead-letter queue. |
| **Ordering** | No cross-process ordering. Fine for analytics; not for a ledger. |
| **Delivery** | At-most-once, and a listener that throws stops the ones after it — the same semantics as Node's own `EventEmitter`. |

<Aside type="caution" title="Know your graduation trigger before you start">
  The moment you need work to survive a restart, cross process boundaries, or be
  retried, you move that side effect behind a real queue or broker and call it from a
  channel. The channel stays; the transport changes. Plan for that migration on day one
  if you suspect it is coming, because the channel boundary is what makes it a
  migration instead of a rewrite.
</Aside>

Being explicit about this matters more than the feature set. A framework that hides
where its boundary is will surprise you at 3 a.m.

## What it is good at

- **APIs with real domain logic.** Order flows, payment state machines, multi-step
  onboarding — anything where a controller that only translates is a win.
- **Side effects that change independently.** Pricing rules, fraud checks, notification
  preferences — the cases where editing one service to add a fifth responsibility is
  where the coupling actually hurts.
- **Message and event pipelines.** Gating, enrichment and fan-out expressed as channels
  subscribing to a namespace.
- **Contracts you can refactor against.** One event map, checked at compile time and
  validated at bind time.
- **Running the same domain outside HTTP.** `app.createContext()` gives a CLI, a cron
  job or a worker the same `call()` a request handler gets, with no server.
- **Betting on a seam.** If you think the HTTP layer is the part most likely to be
  replaced in your project's life, having it behind one import is worth something.

## What it is not for

- **CRUD-only services.** If a controller body is a single database read, the channel
  layer is ceremony, and you should write the route handler.
- **Distributed work.** Multi-process coordination, guaranteed delivery, replay. Use a
  real broker; Gland is not one and does not pretend to be.
- **Teams that want a platform.** No ORM, no config system, no CLI, no admin UI. Gland
  is the composition layer and you pick everything else.
- **Serverless cold starts as the primary constraint.** The container builds the module
  graph on boot — cheap, but not zero.
- **Adopting today without reading the adapter matrix.** The HTTP layer ships under the
  `beta` tag and is changing between minor versions.

## A decision rule

Use Gland if **most** of these are true:

- Side effects are the interesting part of your application, not the plumbing.
- You can name what a piece of work does, and it is not `doEverything()`.
- You will add or remove side effects after launch.
- You are willing to read the adapter matrix before depending on the HTTP layer.
- Your deployment is a single process, or your side effects do not need to cross it.

Stay with Nest — or with plain route handlers — if any of these are true:

- You want an ORM, a CLI, queues, caching and a config system in one dependency.
- Most of your endpoints are read-one-write-one.
- You need delivery guarantees or cross-process coordination now.
- Your team is faster with an ecosystem than with a five-file concept.

Plain route handlers are a legitimate answer, and the page above is not an argument
against them. It is an argument about what to reach for when the domain has more than
one moving part.

## Design commitments

These are the rules the codebase is held to. They are the reason the API is small.

1. **No hidden behaviour.** A method does one thing, and the docs can state what that
   thing is without a caveat.
2. **Composition over configuration.** New capabilities are new packages or channels,
   never new switches on existing ones.
3. **Types are the contract.** The event map is the single source of truth for what
   crosses a boundary.
4. **Fail at startup, not at 3 a.m.** Duplicate channel names, unresolvable
   dependencies and circular references are all detected during bootstrap.
5. **Boundaries are documented, including the inconvenient ones.** The
   [adapter matrix](/reference/http/adapter-matrix) lists what each transport cannot do,
   because a framework that hides its limits will surprise you later.

<Aside type="tip" title="Judging it fairly">
  Gland is young, its HTTP layer ships under the `beta` tag, and nothing on this page is
  a claim that it is ready for a system you cannot afford to debug. If you need a proven
  HTTP stack today, run Gland channels beside Express and keep Express for routing — the
  two compose without either one knowing about the other. If you want to try it, start
  with one channel for one side effect and see whether the indirection earns its keep on
  your code before you commit to it for the rest.
</Aside>
