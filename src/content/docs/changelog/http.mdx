## What is settled

The abstractions are stable enough to build against:

- **The route decorators.** `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`, `@Options`,
  `@Head`, `@Search`, `@All` and `@RequestMapping`, plus the `RequestMethod` enum.
- **`HttpContext`.** The full request and response surface, specified once so every
  adapter implements the same contract.
- **`HttpCore`.** The application object: routing helpers, body parsers, CORS, static
  assets, view engine, `listen()` and `close()`.
- **`HttpBroker`.** The bridge that turns `gland:define:route` into real routes.
- **`HttpServerAdapter`.** The abstract adapter a transport implements.

## What is still in progress

- **Server-sent events.** `ctx.sse()` returns the context without opening a stream. The
  `SSEStream` class in the package is an empty placeholder.
- **`cors`.** `enableCors()` loads the package lazily and it is **not** a dependency of
  `@glandjs/express`. Install it yourself.
- **`setGlobalPrefix()`.** Mounts a router at the prefix; it does not retroactively
  re-register routes that were already bound.
- **Array paths.** The route decorators accept `string | string[]`, but the path is
  concatenated downstream, so an array produces a broken route.
- **App-level events.** A `crashed` / `router:miss` / `request:failed` map is defined in
  the types but not yet wired into the runtime.
- **Fastify adapter.** Referenced by the upstream README; not yet present in the
  repository.

## Beta guidance

- Pin the exact version in production rather than a range.
- Prefer `@glandjs/express` over `@glandjs/http` alone — the latter defines the
  contract but implements no server.
- If you need a proven HTTP stack, run Gland channels beside Express and keep Express
  for routing. The two compose without either one knowing about the other.
